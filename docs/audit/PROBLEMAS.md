### P1 — [stability] songUrlCache (plain HashMap) and bypassCacheForQualityChange (plain mutableSet) are mutated concurrently from the ExoPlayer loader thread, the IO preload coroutine, and the Main thread with no synchronization.
- **Área:** musicservice  |  **Ubicación:** `app/src/main/kotlin/com/music/echo/playback/MusicService.kt:514`  |  **Estado:** ABIERTO
- **Por qué (verificado):** Confirmed genuine unsynchronized data race. songUrlCache is a plain HashMap (l.514) and bypassCacheForQualityChange a plain mutableSet (l.517), both structurally mutated from three distinct threads with no synchronization: (1) ExoPlayer's loader thread inside the ResolvingDataSource resolver reads/writes songUrlCache (l.3962/3970/4091) and reads/removes the bypass set (l.3912/4085) — off-main, evidenced by its internal runBlocking(Dispatchers.IO); (2) Main thread, since scope=CoroutineScope(Dispatchers.Main) (l.305), does songUrlCache.clear()+put in the quality collector (l.865/869) and bypass.add+songUrlCache.remove in refetchCurrentInOpus (l.2814/2815); (3) a Dispatchers.IO coroutine in preloadUpcomingItems (launched l.4953) does containsKey+put (l.4972/4989). Concurrent put during a HashMap resize racing clear/remove can drop entries, return torn reads, or NPE inside HashMap internals. The same file already treats every analogous off-main cache as needing synchronization — loudnessHintCache is ConcurrentHashMap (l.445), videoModeItems is ConcurrentHashMap explicitly "because createMediaSource may be invoked off the main thread" (l.571/577), prebuildingIds is Collections.synchronizedSet (l.579) — so these two were simply overlooked.
- **Fix propuesto:** Change songUrlCache to java.util.concurrent.ConcurrentHashMap and bypassCacheForQualityChange to java.util.Collections.synchronizedSet(mutableSetOf()), matching the existing loudnessHintCache/videoModeItems/prebuildingIds convention. The clear()-then-repopulate at l.865-869 remains a benign logical race; the structural-corruption hazard is what this eliminates.

### P52 — [performance] Playlist widget refresh rasterizes multiple bitmaps on the main thread inside a BroadcastReceiver goAsync coroutine
- **Área:** misc-modules  |  **Ubicación:** `app/src/main/kotlin/com/music/echo/widget/PlaylistWidgetReceiver.kt:72`  |  **Estado:** ABIERTO
- **Por qué (verificado):** Confirmed via code trace. refreshIdleWidgets/refreshIdleWidget launch on CoroutineScope(Dispatchers.Main) (PlaylistWidgetReceiver.kt:72,90,103) and call updateIdleWidget -> createRemoteViews (line 106) -> bindQuickPicks (line 294). ### P53 — [stability] Shared translationCache is a plain (non-thread-safe) mutableMap read/written from both the UI thread and IO coroutines
- **Área:** misc-modules  |  **Ubicación:** `app/src/main/kotlin/com/music/echo/lyrics/LyricsTranslationHelper.kt:58`  |  **Estado:** ABIERTO
- **Por qué (verificado):** translationCache (LyricsTranslationHelper.kt:58) is a plain non-thread-safe LinkedHashMap on a global object. - **Fix propuesto:** Make the cache thread-safe: change line 58 to java.util.concurrent.ConcurrentHashMap<String, List<String>>() (or wrap accessors in @Synchronized). Also mark isCompositionActive @Volatile for cross-thread visibility. No logic change needed since only get/put/clear are used.
